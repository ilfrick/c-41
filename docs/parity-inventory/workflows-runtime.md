# S9 inventory — workflows and runtime

**Pinned comparison:** darktable `upstream/master` at `97912518a5a9a9786aeee3c38116fbc999412ff8`; C-41 at `d908a71bb8345f69f07208ffd92ff88ff2266f47`. This is a capability inventory of cross-cutting workflows/runtime, not a review of the complete upstream commit delta and not a roadmap. Status means **full** only for the scoped capability actually described; **partial** means a useful slice ships but baseline behavior is missing; **absent** means no corresponding product implementation found; **uncertain** means the available source/code sweep is insufficient to assert compatibility. Existing C-41 work is not evidence of full darktable parity.

The pinned source paths below are relative to the upstream tree. C-41 paths are relative to its repository. Findings reflect source inspection at the stated revisions unless a row explicitly labels a post-pin update; tests cited are code-level evidence, not end-to-end parity certification.

## Test evidence and limits

At the pinned C-41 revision, code inspection found focused tests in `crates/c41-core/src/masks/` and `distance_transform.rs`, `crates/c41-db/src/history.rs`, `crates/c41-ui/src/persist.rs`, `stylemodules.rs`, `export.rs`, and the pure layout model in `print.rs`. ICC parsing/transform tests live under `crates/c41-core/src/icc/`. These establish selected local invariants, not darktable-vs-C-41 behavioral equivalence. The inventory task did not run the test suite; no runtime, GTK interaction, printer, script-sandbox, GPU or upstream differential test was executed here.

## Cross-cutting migration and security concerns

- Preserve C-41's established config path, environment variables and SQLite table identity. Database/schema and encoded edit/history changes require explicit migrations and restart/round-trip compatibility tests.
- Multiple instances and masks affect serialization, UI identity, history, copy/paste, styles, undo/redo and export together; adding a control or kernel alone cannot close the workflow gap.
- Any eventual Lua compatibility work needs an explicit capability/security model (filesystem, process, network and UI authority), lifecycle teardown and resource bounds. No sandbox is present today.
- GPU support must be an actual selected execution backend with tested CPU fallback, bounded allocations/tiling and differential results; hardware/container visibility alone is not evidence.
- Color management must distinguish working, proof, display and export profiles. Current output-profile support does not establish printer/display correctness.
- Export/print/batch workflows need safe path/overwrite behavior, predictable selection targeting, cancellation and partial-failure reporting. Those properties were not comprehensively verified in this inventory.

**Scope reminder:** no claim is made that every upstream commit, module, file or runtime behavior between the two revisions was reviewed. This document records the observed cross-cutting capability surface and concrete gaps only.
